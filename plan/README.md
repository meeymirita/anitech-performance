Первая версия планов (расширение готовых лаб тремя-четырьмя сессиями) **отменена по требованию владельца 11.10.2026**: нужны не «добавки», а **полноценные большие работы**, где каждое слово объяснено и показано, как сделать всё.

## Правило 1: каждая лаба — либо полностью самостоятельная, либо продолжение

Схема цепочек:

```
bash  (самостоятельная)
docker ──▶ ansible          (Ansible разворачивает образ из Docker-лабы)
docker ──▶ traefik ──▶ kubernetes
```

**Как это работает без жёстких зависимостей.** В каждой лабе есть папка `starter/` — готовый результат предыдущей лабы цепочки (исходники приложения, `compose.yaml`, образы собираются одной командой). Поэтому у каждой лабы два режима прохождения, оба описаны в её сессии 1:

- **Режим «с нуля»** — берёшь `starter/` и идёшь по методичке; предыдущую лабу проходить не нужно.
- **Режим «продолжение»** — берёшь **свой** результат предыдущей лабы (папка с твоим кодом) и продолжаешь с неё. Шаг «проверка стартового состояния» в сессии 1 подтверждает, что у тебя всё на месте.

Это исправляет жёсткую зависимость, которая была: готовая Kubernetes-лаба требовала код Traefik-лабы (`api/`, образ `traefik-lab-api:v1`) и без него не проходилась.

**Сквозной проект цепочки — CoffeeShop** (Node.js API + статический frontend + PostgreSQL + Adminer): один и тот же, чтобы продолжение было настоящим. У Bash — свой проект CoffeeOps (скрипты обслуживания), который в конце становится деплой-скриптом для CoffeeShop.

## Правило 2: стандарт подробности («каждое слово объяснено»)

Берём за образец Caddy Lab (13 сессий, справка, глоссарий) и замечания владельца по её прохождению (сессия 3: «не понятно, где и какие файлы создавать», «не знаю, что такое WebSocket/SSE», «шаг искали больше часа»). Каждая лаба обязана содержать:

**Теория перед практикой (сессия 1 и первые разделы):** «азбука» — что за предмет, какую проблему решает, как устроено, простыми словами и с аналогией; ничего не предполагается известным.

**У каждого шага:**
1. **«Слова шага»** — каждый новый термин: что это, зачем, аналогия, в одну-две строки (это и есть «каждое слово объясняется»).
2. **«Где мы и что должно быть»** — дерево папок после шага, **какие файлы создать/изменить** и **что должно быть запущено** (таблица «терминал A/B/C — команда — что напечатает»). Не «добавь блок», а «вставь внутрь такого-то блока, вот файл целиком».
3. **Команда разобрана по частям** — каждый флаг, каждая часть; вывод — построчно («что значит эта строка»).
4. **«Как ещё можно»** — альтернативные способы (другая ОС, графическая оболочка вместо командной строки, другой инструмент), чтобы было понятно, «как можно сделать всё», а не один путь.
5. **«Если не получилось»** — типичные ошибки этого шага с точным текстом сообщения, причиной и лечением (по образцу «EADDRINUSE», «404 при двух копиях Caddy»). Диагностика идёт по цепочке «сверху вниз» с командами.
6. **«Под капотом»**, «Проверь себя» (3 вопроса), «🔨 Сломать → починить».

**Бюджет шага — как в Caddy Lab (решение владельца 11.10.2026: «не растягивать сильно»).** По Caddy: в среднем **≈ 2 тыс. знаков на шаг** (медиана ≈ 1,7 тыс., 90% шагов до ≈ 2,9 тыс.; больше — только когда много кода: 3.1 ≈ 7 тыс., из них код ≈ 4 тыс.). Объяснение пишется короткими абзацами «что происходит и зачем», без пересказа очевидного. Чтобы стандарт подробности не раздул шаг: «Слова шага» — **3–6 терминов, по 1–2 строки**; «Как ещё можно», «Под капотом» и длинные разборы вывода — в **сворачиваемых блоках** (в бандле это `deep`), основной текст остаётся коротким; «Если не получилось» — только реально вероятные ошибки (2–4). Жёсткого лимита знаков нет, но шаг заметно длиннее ≈ 3 тыс. знаков без большого кода — повод его разбить на два. Пилот сессии 1 проверяет, что границы выбраны верно.

**У каждой сессии:** критерий приёмки (список «команда → ожидаемый вывод»), «Слова сессии», карточка-шпаргалка, «🔨 Production Hell» без подсказок раз в 2–3 сессии.

**В конце лабы (как у Caddy):** справка — «симптом → причина → что делать», команды с разбором, таблица портов и процессов лабы, глоссарий, вопросы для собеседования, «что дальше».

## Правило 3: размер и устройство

- Размер — как у Caddy Lab: **9–13 сессий по ~4 часа (время ориентировочное: владелец проходит быстрее; после прохождения в подписи сессии ставится «автор за ≈ N ч», как в Caddy)**, 6–8 шагов на сессию (≈ 70–100 шагов на лабу), 150–250 тыс. знаков текста. Готовые «3 сессии × 3 часа» — это уровень введения, а не большой лабы.
- Методички — в том же HTML-формате, что остальные (`<ключ>.html`, бандл), с таймерами и отметками; интеграция по `_checklist-new-lab.md`.
- Версии-стандарт сохраняются: PostgreSQL 18, Node 24, PHP 8.4, nginx 1.30, Traefik v3.7, kind v0.33 / Kubernetes 1.37; остальное — **«сверьтесь» на момент написания** (Helm, `ansible-core`, судьба `ingress-nginx`).
- **Что делают с существующими `docker`, `traefik`, `kubernetes`:** методички переписываются в большой формат в тех же репозиториях. Проверенные примеры и сквозной проект сохраняются, но текст расширяется до стандарта подробности. Ты их ещё не проходила, поэтому прохождения не пропадут.

## Правило 4: честность проверки

Каждая лаба при написании **проверяется запуском** (сухой прогон в Docker/kind, как остальные лабы); в планах команды и версии пока из документации и опыта — не прогнаны. Тяжёлые прогоны (Swarm, kind-кластеры, Prometheus) — с предупреждением, ноутбук греется; Docker Desktop запускается только по твоему согласию. Секреты (токены GHCR, DNS-провайдера, пароль Vault, приватные SSH-ключи) **никогда не лежат в файлах репозитория** — только в переменных окружения и `.gitignore`.

## Последовательность работ

Две разные последовательности: что **проходит** владелец и что **пишет и проверяет** ассистент. Они совпадают по порядку лаб, но идут со сдвигом: лаба пишется заранее, чтобы к моменту прохождения она была готова.

### А. Порядок прохождения

```
Caddy (идёт, сессии 4–13) ─▶ Bash ─▶ Docker ─▶ Traefik ─▶ Kubernetes + Helm ─▶ Ansible
```

| № | Лаба | ~Часы | Что нужно до неё | Почему именно здесь |
|---|---|---|---|---|
| 0 | **Caddy** (текущая) | осталось ~9 сессий | — | решение владельца 06.10: проходит только её, пока не закончит |
| 1 | **Bash** | 26 (сокращено 11.10: было 36) | — | нужен всем следующим (скрипты, entrypoint, деплой); на нём же впервые используется контейнер `docker run` в минимальном объёме |
| 2 | **Docker** | 48 | желательно Bash | база для всей цепочки; в конце — образ CoffeeShop в GHCR и `starter/` |
| 3 | **Traefik** | 40 | Docker или `starter/` | продолжает Docker-стек; после Caddy reverse proxy уже знаком, остаётся сравнить; сразу в цепочке «Docker → Traefik → Kubernetes», пока стек свежий |
| 4 | **Kubernetes + Helm** | 52 | Traefik (или `starter/`) | самая тяжёлая и самая востребованная; берёт стек и Ingress из Traefik-лабы; идёт сразу за ней, чтобы продолжение было настоящим |
| 5 | **Ansible** | 40 | Docker (образ и compose) или `starter/` | боковая ветка, нужна меньше всего для типовой работы Laravel-разработчика; идёт последней, когда Docker и Kubernetes уже освоены; зато разворачивает всё построенное «на серверы» |
| — | Docker Swarm | (внутри Docker, сессия 11, одна) | | не отдельный шаг; сессию можно пропустить без потерь для следующих лаб |

Итого ~216 часов. Что открывается после этой цепочки: **Centrifugo** и **Go Start** желательно после Docker (по `_order.md`), **Go Pro** — после Kubernetes и Go Start; их можно вставлять в любую точку после соответствующего шага.

### Б. Порядок создания (что делает ассистент)

Лаба создаётся **заранее, но не раньше предыдущей**: так `starter/` строится из уже проверенного кода предыдущей. Пока владелец проходит Caddy, готовится следующая.

| Этап | Что | Ворота (когда считается готовым) |
|---|---|---|
| **0** | Заготовки репозиториев `bash-lab`, `ansible-lab` и планы во всех пяти папках | **сделано 11.10.2026** |
| **1** | **Bash**: методичка 9 сессий, среда `bash:5`, сухой прогон всех скриптов в контейнере, вычитка | все скрипты проходят в контейнере; `shellcheck` без замечаний |
| **2** | **Docker**: переписать `docker.html` (12 сессий), прогон в Docker, **`starter/` — CoffeeShop + `compose.yaml` + образ в GHCR** | `docker compose up` на чистой папке поднимает сайт; образ собирается |
| **3** | **Traefik**: переписать `traefik.html` (10 сессий), прогон (включая mkcert, canary; ACME/DNS — «на сухую»), `starter/` | стек CoffeeShop за Traefik, все middleware отработали |
| **4** | **Kubernetes + Helm**: переписать `kubernetes.html` (13 сессий), прогон на kind (с Calico для `NetworkPolicy`), umbrella-chart | `helm install` на чистом kind даёт рабочий сайт; `upgrade`/`rollback` проверены |
| **5** | **Ansible**: методичка 10 сессий, стенд из контейнеров с `sshd`, прогон playbook’ов (в т. ч. `changed=0` на втором запуске), `starter/` | выкатка CoffeeShop на «серверы» воспроизводима с нуля |
| **6** | Интеграция каждой готовой лабы по `fixes/common/_checklist-new-lab.md` (карточка, реестры, прогресс, SEO), записи в `_order.md`, `_proofread.md`, `_verification.md`, `changelog.html` | `python3 tools/check-site.py` → OK |

**Конвейер одной лабы (повторяется на этапах 1–5):**
1. Каркас: оглавление сессий, «Слова сессии», сквозной проект, структура папок.
2. Написание по 3–4 сессии за раз (в стандарте подробности, раздел «Правило 2»).
3. **Сухой прогон** каждого шага запуском (Docker Desktop — только с согласия; предупреждать перед тяжёлым; после — чистить только созданное).
4. Вычитка: построчное чтение, сверка кода между шагами, находки в `fixes/<направление>/<лаба>.md`.
5. Справка (ошибки, команды, порты, глоссарий, вопросы), `starter/`.
6. Статус «методичка вычитана и проверена запуском» — по `_verification.md` (что не проверено — перечисляется честно).
7. Интеграция (этап 6).

**Правила очерёдности:**
- Лаба N+1 **не пишется целиком**, пока у N нет проверенного `starter/` (допустимо писать азбуку/сессию 1 заранее).
- Старые `docker.html`, `traefik.html`, `kubernetes.html` остаются на сайте, пока не готова замена; владелец их **не проходит** — ждёт новые.
- Правки Caddy-методички по замечаниям владельца имеют приоритет над новыми лабами (владелец сейчас её проходит).
- Пока владелец проходит Caddy, **её методичку без замечаний не трогаем**.

## Процесс написания: как добиться, чтобы лабы были сделаны нормально

Выше — порядок лаб и общий «конвейер». Ниже — сам процесс, с причинами: каждый пункт закрывает конкретную проблему, которая уже случалась в этом репозитории.

| Проблема из прошлого | Что в процессе её закрывает |
|---|---|
| Готовые Docker/Traefik/Kubernetes «маленькие, почти ничего не рассказывается» | стандарт подробности + **автопроверка структуры** (пункт 2): шаг без «Слов шага» или «Если не получилось» не собирается |
| Caddy сессия 3: «не понятно, где и какие файлы создавать», шаг искали больше часа | блок «Где мы и что должно быть» обязателен; **сухой прогон «как студент»** (пункт 4) ловит такое до владельца |
| Вычитка Go Start/Go Pro сделана другой моделью и не принята | статус «принята» ставит **только владелец** (пункт 6); без её «да» лаба не считается готовой |
| Бывало, что `jsub` правил скрытый текст, а видимый — нет; битый JSON ломал страницу | **генератор из исходников** (пункт 1) вместо ручной правки бандла; проверка видимого текста в Chromium |
| «Проверено» на стендах, отличавшихся от студенческих | сухой прогон только по тексту методички в чистой среде; отличия — в `_dryrun-assumptions.md` |

### 1. Сначала инструмент: исходники в Markdown → готовая методичка
Сейчас в репозитории **нет** генератора методички: все существующие приходили готовым HTML-бандлом (из дизайн-чата), а править бандл вручную через `bundle.py` годится для правок, но не для написания 200 тыс. знаков с нуля. Поэтому до первой сессии Bash:
- завести формат исходников: `<лаба>/src/session-NN.md` (по файлу на сессию; шаги, блоки «Слова/Где мы/Если не получилось…» — размеченные заголовками) и `<лаба>/src/theory-*.md`, `reference-*.md`;
- написать `tools/build-manual.py`: исходники → `window.LAB` → `<ключ>.html` (в шаблоне, как у остальных лаб), с проверкой JSON и пересборкой оглавления;
- проверить на готовой маленькой методичке (собрать из её же текста и сравнить вид), и только потом писать контент.
Выгода: каждую сессию можно писать, читать и править отдельным файлом (разговор не упирается в размер бандла), а git показывает человеческий diff.

### 2. Автопроверка структуры (`tools/check-manual-structure.py`)
Для каждого шага проверяет наличие: «Слова шага», «Где мы и что должно быть» (дерево файлов + что запущено), команды с разбором, «Ожидаемый результат», «Если не получилось», «Проверь себя» (3 вопроса); у сессии — приёмка и 🔨; у лабы — справка, глоссарий, вопросы. Падает, если чего-то нет, — это формальный минимум «подробности». Вызывается из `check-site.py`.

### 3. Пилот на одной сессии, потом партии
1. **Пилот:** одна сессия Bash (1) полностью, в стандарте — показывается владельцу в браузере. Её «да/нет/поправь» фиксирует **шаблон шага** (длина, тон, глубина разбора, число аналогий). Дёшево поправить сейчас, дорого после девяти сессий.
2. **Партии по 3 сессии** (не по одной и не всё сразу): 1–3, 4–6, 7–9. После партии — пункты 4 и 5, и только потом следующая.
3. Один и тот же сквозной проект на всей лабе; перед партией сверка «состояние проекта на конец прошлой сессии» (файлы и версии не расходятся).

### 4. Сухой прогон «как студент» — по тексту, не по памяти
- Чистая папка/контейнер без моих заготовок; выполняются **только** команды и файлы из методички, копированием.
- Любое место, где пришлось «догадаться», достроить файл, поправить команду, — **находка** (запись в `fixes/<направление>/<лаба>.md`), и текст правится до того, как увидит владелец.
- Окружение записывается (ОС, версии, порты), отличия от студенческого — в `_dryrun-assumptions.md`.
- Тяжёлое (Docker Desktop, kind, Prometheus) — с твоего согласия и с предупреждением; после — чистить только созданное.

### 5. Вычитка отдельным проходом
Не тем же заходом, что писался текст: построчное чтение, сверка кода и версий между шагами и сессиями («в 3.2 файл такой, в 5.1 уже другой?»), ссылки «раздел N / сессия N», проверка видимого текста в Chromium. Находки — в `fixes/`; исправленное перепроверяется запуском.

### 6. Статусы и кто их ставит
`⬜ план` → `🟡 написана` (ассистент) → `🟢 проверена запуском` (ассистент, с перечнем непроверенного в `_verification.md`) → `✅ принята владельцем` (**только она**) → `пройдена` (после прохождения). Правки из её замечаний при прохождении идут тем же путём, что в Caddy: `docs/change_lab.md` → таблица «обработано» → правка → запись в журнал.

### 7. Что считается «готово» для лабы
Все сессии собраны генератором; автопроверка структуры зелёная; сухой прогон по всем шагам, находки закрыты; есть справка, глоссарий, вопросы, `starter/` (где предусмотрен); `check-site.py` OK; владелец приняла пилот и партии.

### Как пишутся лабы: решение владельца (11.10.2026)
