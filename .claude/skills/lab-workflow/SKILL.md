# Workflow лабораторий anitech-performance

У владельца репозитория правило: после любой законченной правки проходить
весь список обязательных действий самостоятельно, без напоминаний. Полные
чек-листы уже существуют и поддерживаются в самом репозитории — **этот
скилл их не копирует и не пересказывает заново** (две копии одного и того
же списка быстро расходятся, и тогда непонятно, какая верная). Он нужен
как шаблон мышления и принудительный финальный шлюз: классифицировать
задачу → найти нужный раздел канонического документа → выполнить → сверить
скриптом → не отчитаться о «готово», пока шлюз не пройден или расхождения
не объяснены пользователю.

## Канонические источники (читать их, не пересказ ниже)

| Документ | Что в нём |
|---|---|
| `CLAUDE.md`, раздел «Порядок действий после ЛЮБОЙ правки» | таблица «что затронуло → что пересобрать», обязательные записи, порядок git |
| `fixes/common/_checklist-new-lab.md` | полный пошаговый чек-лист для новой/переинтегрируемой лабы (все ~12 пунктов по файлам) |
| `fixes/common/_state-log.md` | журнал по датам — читать ПЕРЕД началом, чтобы не переделывать уже сделанное |
| `fixes/common/_plan-schemes-results.md` | стандарт «схемы + настоящие Ожидаемые результаты» и порядок работы по лабе (пилот — JS) |
| `fixes/common/_verification.md`, `_proofread.md`, `_order.md` | статусы проверки, вычитки, порядок/зависимости лаб |
| `fixes/common/_dryrun-assumptions.md` | чем мой сухой прогон отличается от реального прохождения — не присваивать себе "проверено", если это не так |
| README каждой лабы, строка «Статус:» | текущий фактический статус — источник правды, не память |

Если по ходу работы эти документы противоречат тому, что ты видишь в коде —
верить коду и файлам, а не памяти; документы тоже могут устареть.

## Шаг 0 — классифицировать задачу

| Похоже на... | Это сценарий | Раздел-ориентир |
|---|---|---|
| «добавь лабу», «интегрируй <лаба>», лаба была только планом/заглушкой | **Новая лаба** | весь `_checklist-new-lab.md` |
| «перепиши <лаба> в формат Caddy», «доведи до 10 сессий», смена структуры сессий | **Переписывание до стандарта** | тот же чек-лист, но без пп. про сам подмодуль/README с нуля — только то, что реально изменилось (сессии, карточка, реестры с числом сессий) |
| «поправь шаг N.M», «добавь абзац», «исправь опечатку/код в методичке» | **Точечная правка методички** | CLAUDE.md, строка таблицы «текст методички» — только `bundle.py`, не сырой `sed`/`grep` |
| «вот находка вычитки, почини» | **Фикс из `fixes/`** | правка + запись в `fixes/<направление>/<лаба>.md` (что исправлено) + состояние в `_verification.md`/`_proofread.md`, если статус менялся |
| «смени статус/сложность/статус проверки» | **Статус-правка** | README лабы, `_verification.md`/`_proofread.md`, `index.html` (`note`/`difficulty`), без переписывания контента |

Не бойся отнести задачу сразу к двум сценариям — например, фикс находки на
проверенной лабе может по итогу понизить статус с ✅ до 🟡 (так было
13.10 с Express и Laravel Performance): в этом случае выполняются оба
списка действий.

## Шаг 1 — сделать саму правку

- Методички — ТОЛЬКО через `fixes/common/_tools/bundle.py` (`jsub`/`jre`/`transform`).
  Сырой `sed`/`grep` по `.html` методички не работает (текст — сжатый JSON
  в `window.LAB`) и может дать невалидный JSON — страница перестанет
  открываться. Так уже ломали Vue и Laravel.
- Новые реестровые записи (карточка, `LABS`, `ORDER`, `routeLanes` и т.д.) —
  списывать с ближайшей уже интегрированной лабы, не выдумывать с нуля.
- Если правка — результат «сухого прогона» лабы в Docker, учитывать
  `_dryrun-assumptions.md`: не формулировать находку как «проверено на
  студенческом стенде», если прогон был на другом окружении.

## Шаг 2 — пересобрать то, что зависит от правки

Таблица «Правка → что ещё сделать» в `CLAUDE.md` — обязательна к
прохождению целиком, не только «очевидных» строк. Частые промахи:
- поменялись сессии/шаги лабы → `tools/build-toc.py`, `tools/build-seo.py`,
  `works/js/prereq.js` (сессии/часы), `works/js/lab.js` (`sessions`);
  если менялся порядок/число лаб — `tools/build-progress.py`, затем
  `tools/build-seo.py` ещё раз (иначе у `progress.html` пропадают title/noindex);
- новая/обновлённая обложка → синхронизация бакета сама по себе (Actions),
  руками в консоль Yandex не лезть;
- **лаба переписана, расширена или поменяла состав сессий → ОБНОВИТЬ ВСЮ запись лабы в `works/js/lab.js`, а не только `sessions`:** `desc` (после «:» — список тем через запятую), `stack` и **столько же** описаний в `stackInfo` (иначе последние плитки пустые), `learn` (код — реальные блоки методички), `sessions` (число и часы = методичка), `arch` вместе с `live.nodes` (подписи, сети, имена доменов), `faq`; затем `desc/stack/note` карточки в `index.html`, `works/js/prereq.js`, README лабы и корня. 18.10.2026 у Traefik методичку переписали, а страница лабы осталась со старым FAQ, пустой плиткой стека и обрезанным списком тем — нашла владелец. Теперь `tools/check-site.py` ловит пустые плитки, desc без «:» и расхождение числа сессий, но смысл текста (faq, arch, learn) проверяется только глазами (шаг 3, пункт 2б);
- шаблон страницы методички менялся → `bundle.patch_template`, помнить,
  что шаблон общий у всех лаб (если проблема системная — сказать об этом
  пользователю, а не чинить только одну лабу).

## Шаг 3 — проверить, а не поверить себе на слово

Любое утверждение о работающем коде или тексте — подтверждать запуском,
а не выводить логически:
1. `python3 tools/check-site.py` → должно быть `OK`.
2. Если менялся ВИДИМЫЙ текст методички — открыть `<лаба>.html#step-N-M`
   headless Chromium и прочитать `body.innerText` на новую фразу.
   `bundle.load`/`jsub` могли заменить только скрытый `text`, а не HTML,
   или наоборот — это не ловится одним `check-site.py`.
2б. Если менялась запись лабы в `lab.js` или карточка — открыть **страницу лабы** `works/<ключ>.html` в headless Chromium и прочитать `body.innerText` целиком: нет ли старых чисел сессий и часов, старых имён (домены, сети), пустых плиток стека, «тем внутри 0», устаревших вопросов «Проверьте себя» и схемы архитектуры (как в `fixes/common/_tools/verify/`: Playwright + `--host-resolver-rules="MAP cdnjs.cloudflare.com 0.0.0.0"`).
3. `node --check` для изменённых `.js`.
4. Запустить `python3 .claude/skills/lab-workflow/scripts/gate.py` —
   дополнительно проверяет записи за сегодня в changelog/state-log и
   чистоту git (см. ниже). Он НЕ проверяет видимый текст и README — те
   два пункта выше и README остаются на тебе.

## Шаг 4 — записи (легко забыть, уже случалось дважды)

- `works/changelog.html`: новый блок в `DAYS` **перед `];`** (не внутри
  `renderStats()` — так однажды блок за день потерялся, `node --check`
  такое не ловит), честно, включая что было криво.
- `fixes/common/_state-log.md`: новая запись **в начало** раздела
  «Журнал», что сделано / что НЕ сделано или не проверено / что решать
  владельцу.
- Если это находка вычитки — `fixes/<направление>/<лаба>.md`.
- Если менялся статус/сложность/вычитка — README лабы (`Статус:`),
  `_verification.md`, `_proofread.md`, и при необходимости строки в
  самом `CLAUDE.md` («Актуальное состояние»).
- Важное о владельце (не о репозитории) — в автопамять, не сюда.

## Шаг 5 — git, только по прямой просьбе

Если пользователь НЕ просил коммитить/пушить — остановиться после шага 4
и явно сказать, что изменения не закоммичены. Если просил:
1. `git status` до, посмотреть, что реально меняется.
2. Сабмодуль(ы) с контентом → `works`/`fixes`, если трогали → родитель
   последним с бампом версий подмодулей.
3. Перед пушем родителя — проверка «ни один подмодуль не опережает
   origin» (команда есть в `CLAUDE.md`, раздел «Правила git», и
   встроена в `gate.py`).
4. `git show --stat` после каждого коммита — убедиться, что не попало
   лишнее (однажды в коммит методички попал чужой файл).
5. После пуша — `gh run list --limit 4`: зелёными должны быть
   `Check site` и `Sync bucket` (синхронизация один раз час падала молча —
   без неё правки не попадают на сайт).

## Шаг 6 — финальный отчёт пользователю

Не писать «готово», пока не прогнан `gate.py` (или не объяснено, почему
какой-то его пункт не применим к этой конкретной правке). В ответе —
коротко и честно:
- что сделано;
- что НЕ сделано или не проверено (например: задание не решено, Chromium
  не смотрели, прохождение не было — называть прямо, не умалчивать);
- что осталось решить владельцу.

Ничего не выдавать за проверенное, если проверка не запускалась.
